# Схема работы: PM и исполнители в VS Code

Как запустить команду агентов на своём проекте и вести её день. Установка скиллов — в README.

```
 ВЛАДЕЛЕЦ ──── пишет только PM ────▶  PM (вкладка 1)
                                       │  SendMessage: задачи
                  ┌────────────────────┼────────────────────┐
                  ▼                    ▼                    ▼
          Исполнитель A        Исполнитель B        Облачный агент
          (вкладка 2)          (вкладка 3)          (claude.ai/code)
          своя выкладка        своя выкладка        своя ветка + PR
                  │                    │                    │
                  └── SendMessage: ОТЧЁТ ──┘       комментарий в PR
                                       ▼
                       PM: приёмка → main → выкат → отчёт владельцу
```

---

## Этап 1. Открыть сессии

1. В VS Code откройте проект. Сессий Claude Code — **одна PM и 1–3 исполнителя**, каждая в своей вкладке.
2. **Все сессии — в одном режиме прав.** Если режимы разные, сообщение между сессиями ждёт ручного одобрения, и команда встаёт.
3. Облачный агент нужен, только если есть задачи, которые целиком делаются в GitHub. Он получает сообщения, но **ответить в сессию не может**: его канал обратно — комментарий в PR.
4. Дешёвая модель (GLM, Kilo, Codex) — отдельным расширением, связь через файл задач (этап 5).

## Этап 2. Первое сообщение PM

Вставьте во вкладку PM:

```text
Ты PM проекта <название>. Прочитай скиллы pm-orchestration и ux-ui-review.
Исполнители — соседние сессии: найди их через ListAgents.
Код пишут они, ты ставишь задачи, принимаешь своим прогоном и выкатываешь.
Цель: <что должно быть готово и к какому сроку>.
Начни с фаз и задач, раздай исполнителям, мне — только решения и итог.
```

## Этап 3. Первое сообщение каждому исполнителю

```text
Ты исполнитель. PM — соседняя сессия, её имя найдёшь в ListAgents.
Задачи приходят от PM сообщением. Отчёт — SendMessage PM, первая строка:
«ОТЧЁТ · <номер задачи> · готово» или «· вопрос».
Работаешь только в своей git worktree от origin/main. Не пушишь, не выкатываешь,
на бой не ходишь без задачи PM. Спорное — вопрос PM, а не решение самому.
```

После этого владелец исполнителям не пишет. Все задачи идут через PM.

## Этап 4. Как PM раздаёт работу

| Задача | Кому |
|---|---|
| механика: строка в список, текст, перенос по образцу | дешёвая модель через файл задач |
| безопасность, данные людей, выкат, скрипты сервера | сильный исполнитель (сессия Claude) |
| ревью чужого кода, вычитка документа за другим | второй исполнитель: ревьюер ≠ автор |
| продуктовая развилка | никому, сначала владелец |

Каждая задача содержит: выкладку (`git worktree add -b <ветка> <путь> origin/main`), факт «почему», правило, пробы, порчу и что не трогать. Шаблон — `skills/pm-orchestration/references/task-spec-template.md`.

## Этап 5. Файл задач для модели без SendMessage

1. PM пишет задачу в `.kilo/tasks/<исполнитель>-task.md`, раздел `## Задача N` и пустой `### Отчёт · задача N`.
2. Владелец вставляет исполнителю одну строку от PM:
   `Выполни задачу N из файла .kilo/tasks/<исполнитель>-task.md, отчёт допиши в раздел «Отчёт · задача N»`.
3. Возврат на доработку — новая задача `Nb` в том же файле.

## Этап 6. Приёмка: PM не верит отчёту

1. Хеш стоит на свежем main, в диффе только файлы задачи.
2. Гейт проекта — **на чистой копии хеша** (`git worktree add --detach`), со своей тестовой базой.
3. Порча: откатить правку (не тесты) → пробы задачи **красные** → вернуть → зелёные.
4. Интерфейс — ревью скиллом `ux-ui-review`. Рискованное — три скептика.
5. Итог исполнителю: `ПРИНЯТА` с цифрами или `ВОЗВРАТ` пунктами.

Push в main, слияние и выкат делает только PM.

## Этап 7. Общие ресурсы машины

| Ресурс | Правило |
|---|---|
| выкат и его предполёт | один выкатывающий. На время выката PM пишет исполнителям: без тестов, сборок и браузеров |
| бой (рабочий сервер) | исполнитель — только чтение и только по задаче PM; входы на бой общие и ограничены окном |
| Docker, диск, порты | до действия — строка владельцу ресурса. Чистильщик диска не трогает кэши, пока идёт выкат |
| общий чекаут | только чтение. Черновики документов исполнители кладут в отдельную папку, в проект их переносит PM |

## Этап 8. Владелец в течение дня

- Видит сообщения PM, в них только итог, блокеры и решения с вариантами.
- Отвечает одним словом на развилку, остальное решает PM.
- Остановил PM кнопкой — исполнители продолжают. Остановить их — сказать PM.
- Хочет новую задачу — пишет PM, а не исполнителю.

## Этап 9. Конец дня

1. PM: отчёт владельцу — что на бою, чем доказано, что за ним.
2. Исполнители: выкладки и тестовые базы убраны, браузеры закрыты, работа «после сдачи» записана в память, чтобы очередь пережила сжатие контекста.
3. PM: доска и журнал прогресса обновлены. Черновики, на которые ссылается отчёт, не удалять до приёмки владельцем.

## Частые сбои

| Что видите | Причина | Что делать |
|---|---|---|
| сообщение соседу «queued», ответа нет | разные режимы прав или сосед ждёт одобрения | одинаковый режим; одобрить во вкладке соседа |
| `ENOENT … .sock` | сосед перезапустился, адрес сменился | PM снова делает ListAgents и пишет по имени |
| предполёт выката красный «идут прогоны» | исполнитель гоняет тесты | PM: «до конца выката без тестов» |
| облачный агент молчит | не умеет писать обратно | читать его PR: `gh pr view <n> --comments` |
| исполнитель сдал не всё | задачу дописали, когда он уже работал | PM сверяет сдачу по разделам, а не по резюме |
