# Задачи поэтапно: фазы, партии, очередь

Как большая работа превращается в поток маленьких принимаемых задач, чтобы ничего не
потерялось и исполнители не мешали друг другу.

## 1. Разбить до атома

```
цель владельца
 └─ фазы        (результат, который можно показать: «копии каждые 6 часов на бою»)
     └─ срезы   (одна задача исполнителю, одна ветка, один хеш на приёмку)
         └─ шаги (действие → проверка)
```

- У каждой фазы и каждого среза — **проверяемый итог**: хеш, число проб, строка журнала, экран.
  «Улучшить X» — не срез. «Трекер не видит отключённого в очереди: проба красная без правки» — срез.
- Фазы называешь владельцу **один раз, одним списком**, дальше работаешь молча и возвращаешься,
  когда фазы закрыты или упёрся в решение владельца.
- Решение строится на 2–3 независимых источниках (код, бой, документ), а не на одной выдаче.

## 2. Порядок: критический путь и 80/20

1. Сначала то, на чём стоит выкат или что грозит данным людей.
2. Потом то, что даёт больше всего пользы за меньше всего работы.
3. Параллелить только независимое: разные репозитории, разные файлы. Две задачи в одном
   файле-перекрёстке — последовательно.
4. Срочное, дописанное в очередь позже, ставь первым в `order` и помечай «СРОЧНО» в заголовке —
   исполнитель мог уже начать следующую.

## 3. Кому какую задачу

| Задача | Исполнитель |
|---|---|
| механическая: строка в список, текст, перенос по образцу | дешёвая модель через файл задач |
| безопасность, область видимости, данные людей, журналы с личными данными | сильный исполнитель (сессия Claude, облачный агент) |
| выкат, скрипты сервера, миграции с заполнением | сильный исполнитель + приёмка PM с разбором диффа по строкам |
| продуктовая развилка | никому: сначала владелец |

## 4. Нумерация и жизнь задачи в очереди

| Номер | Значит |
|---|---|
| `N` | задача |
| `Nb`, `Nc` | возврат на доработку N (новые коммиты поверх, без amend) или срочная вставка рядом с N |
| `G1…` | задачи облачного агента (свой префикс на каждого исполнителя, чтобы не путать) |

Статусы в `accepted`: `на проверке PM` → `ПРИНЯТА (цифры)` / `ВОЗВРАТ: задача Nb` →
`в main` → `на бою`. Урок из возврата — строкой в `lessons` шапки: следующая задача
исполнителя начинается с чтения уроков.

## 5. Партия выката

- Принятые срезы копятся в **партию**. Партия = один выкат, один прогон проб на бою.
- Порядок в партии — по фактам:
  - новые поля в ответах сервера → сначала сайт (он должен уметь их пропускать);
  - новые ручки, которые сайт уже зовёт → сначала сервер;
  - обе стороны строгие → две партии.
- Перед партией: миграции по именам и что каждая делает; заполнение отрепетировано на копии
  боя; при 3+ новых ручках — отдельный read-only проход по безопасности.
- Сосед готов к выкату, а везёшь ты — возьми его срез в ту же партию. Закончил — строка соседу.

## 6. Три скептика перед решением (для рискованных срезов)

Перед тем как принять срез, который трогает безопасность, данные или выкат, — три
независимых проверяющих параллельно, read-only:

1. **Технический** — верен ли код и доказывают ли пробы именно это правило.
2. **Логический / DevOps** — что сломается на бою, в каком порядке, как откатить.
3. **Безопасность** — область видимости, роли, утечки полей и личных данных.

Вход у каждого: хеш, stat диффа, заявление исполнителя, твой черновик решения, пункт
требования. Выход: таблица «утверждение · вердикт · доказательство». Стоит заметно лимита —
для механических срезов не запускать.

## 7. Пульт, чтобы не терять нить

- Доска срезов в файле PM: срез · исполнитель · хеш · статус · следующий шаг. Обновлять
  на каждое событие.
- После сжатия контекста, перезагрузки или паузы — сначала пульт и скрипт состояния
  (что в main, что на бою, чьи выкладки впереди), потом действия.
- Факт — из команды, а не из памяти разговора: доска — последняя запись, истина — вывод скрипта.
